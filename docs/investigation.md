# 調査記録と設計判断

このツールが何のために、どういう根拠で今の形になったかの記録。
コードだけ読んでも分からない「なぜ」を残すためのもの。

## 発端

DMM GAME PLAYER 経由で War Thunder を起動すると、ミサイル発射に割り当てたキーが効かなくなる。
代わりにスクリーンショットが連写される。DMM GAME PLAYER の設定画面ではショートカットキーを
別のキーに変更できるだけで、機能そのものを無効化する手段がない。

「無効化できないなら、プロセスごと落とせばいいのでは」という発想が出発点。
ただし常用するなら手動でタスクマネージャを開くのは現実的でないので、常駐ツールにする。

## 調査で確かめたこと

すべて実機 (Windows 11 Pro 26200) での実測。推測と実測を混ぜないよう、
確認できなかったことは末尾の「未解決」にまとめてある。

### 対象プロセスの素性

| 項目 | 実測値 |
| --- | --- |
| 実体 | `C:\Program Files\DMMGamePlayer\resources\GamesPlayAssist.exe` |
| バージョン | 0.2.1 (18,253,752 bytes) |
| 所有者 | ログオン中のユーザー本人 |
| 整合性レベル | Medium (`S-1-16-8192`) |
| サービス登録 | なし |
| 自動起動登録 | なし (Run キー・スタートアップフォルダ・タスクスケジューラのいずれにも無し) |
| 実装 | Tauri (Rust) + WebView2 (`EmbeddedBrowserWebView.dll` をロード) |

親プロセスは DMM GAME PLAYER だが、**親が終了しても生き残る**。
ここが厄介なところで、ランチャーを閉じてもキーは奪われたままになる。

### 管理者権限なしで終了できるか → できる

非昇格の PowerShell から `OpenProcess(PROCESS_TERMINATE)` を呼び、ハンドル取得に成功することを確認した。
対象は同一ユーザー・同一整合性レベル (Medium) なので、UAC 昇格は一切要らない。

これが成立しなければ「管理者権限なしで動く」という要件が崩れるため、最初に潰した論点。

### キーを奪う仕組み → RegisterHotKey

プロセスが所有するウィンドウを列挙したところ、`global_hotkey_app` というクラス名の不可視ウィンドウがあった。
これは Rust の `global-hotkey` crate (Tauri エコシステム) が作るメッセージ専用ウィンドウで、
Windows では内部的に `RegisterHotKey` を使う。

`RegisterHotKey` で登録されたキーはシステム全体で横取りされ、登録元プロセスにだけ配送される。
フォアグラウンドのゲームには届かない。War Thunder が DirectInput を使っていようが関係なく効く。

そして **`UnregisterHotKey` は登録したスレッド自身からしか呼べない**。
他プロセスのホットキーを外部から解除する API は Windows に存在しない。
つまり設定でも無効化できず、外部からも解除できない以上、**プロセスを終了させる以外に手が無い**。
これがこのツールの存在理由。

### 設定ファイルとログによる裏取り

`%APPDATA%\GamesPlayAssist\<hash>\user-settings.json`:

```json
{"shortcuts":{"overlay":{"code":"Numpad9","modifiers":["CONTROL"]},
              "screenshot":{"code":"KeyX","modifiers":["ALT"]}}}
```

`%APPDATA%\GamesPlayAssist\logs\play-assist-app.log` に、症状そのものが記録されていた。
4 秒間に 4 回、ショートカット経由 (`is_shortcut: true`) でスクリーンショットが撮られている:

```
"Screenshot taken successfully: ScreenshotResult { ... is_shortcut: true }"
```

同じログに `RESET_SHORTCUT` を押した記録も残っており、
「変更はできるが無効化はできない」という UI 仕様とも整合する。

### ホットキーは常時登録されているわけではない

`RegisterHotKey` を全仮想キーコードに対して総当たりし、
`ERROR_HOTKEY_ALREADY_REGISTERED` (1409) が返るものを調べた。
このときターミナルがフォアグラウンドだったが、設定されているはずの `Alt+X` は登録されていなかった。

起動引数に `--window-name "War Thunder"` があることから、
**対象ウィンドウがフォアグラウンドのときだけホットキーを登録している** と考えられる (推測)。
なおスキャンで検出された `F12` / `Shift+F12` は本プロセスとは無関係で、
Steam など他アプリのものと思われる (未確認)。

いずれにせよ、登録が動的でも静的でも、プロセス終了で解放される点は変わらないので設計には影響しない。

### ゲームとの関係

ログには次の流れが残っていた:

```
"ゲームプロセスが終了しました。"
"アシスタント機能を終了します。"
```

`GamesPlayAssist` はゲーム本体のプロセスを監視しており、**ゲームが終了すると自分から終了する**。
また、ゲーム本体が見つからないときに
`プロセスの終了コードを取得できませんでした ... exe_file_path = "...\aces.exe"`
というエラーを出していた。子プロセスのハンドルを持っているのではなく、
実行ファイルのパスで探していることが分かる。

起動引数は次の形をしている (識別子は伏せた):

```
GamesPlayAssist.exe --window-name "War Thunder" --startup-exe-file-path "...\launcher.exe"
                    --product-id "wt" --game-title "War Thunder"
                    --game-exe-file-path "...\win64\aces.exe" --app-version "5.5.16" ...
```

## 設計判断

### なぜ「ゲーム本体が起動してから」殺すのか

引数に `--startup-exe-file-path` があるため、`GamesPlayAssist` がランチャーの起動を
仲介している可能性を完全には否定できなかった。無条件に即終了させる実装だと、
最悪の場合ゲームが起動しなくなる。

一方、**ゲーム本体が既に起動している状態で終了させても安全であることは実測で確認済み**
(ゲームプロセスは生存し、キーは解放された)。
そこで、確実に安全と分かっている条件でだけ終了させることにした。

急ぐ人のために `--force` で無条件終了もできるようにしてある。

### なぜゲームの実行ファイル名をハードコードしないのか

`aces.exe` を直接書けば実装は簡単になるが、War Thunder 専用になってしまう。
`GamesPlayAssist` 自身が `--game-exe-file-path` でゲーム本体のパスを持っているので、
それを読めば DMM のどのタイトルでも動く。公開して配布する以上、こちらを選んだ。

### なぜ PEB を直接読むのか

他プロセスのコマンドラインを取る方法は主に 2 つある。

- WMI (`Win32_Process.CommandLine`) — COM の初期化が必要で、常駐プロセスとしては重い
- `NtQueryInformationProcess` → PEB → `RTL_USER_PROCESS_PARAMETERS` を `ReadProcessMemory` で読む

後者を選んだ。依存が増えず、必要な権限も
`PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` だけで済む (非昇格で通ることは実測済み)。

代償として構造体オフセットを直書きしているため **x64 専用**になる。
32bit 版でビルドされないよう `compile_error!` を置いてある。

### なぜイベント駆動ではなくポーリングなのか

非昇格でも WMI のプロセス生成イベントを購読できることは確認した (これも実測)。
ただし `WITHIN 1` の指定は内部的に 1 秒ポーリングであり、実質的な違いは無い。
`CreateToolhelp32Snapshot` を 1 秒ごとに 1 回叩くだけなら CPU 負荷は無視できる範囲なので、
COM 依存を持ち込まない素朴なポーリングにした。

### なぜ機能を増やさないのか

トレイアイコン、設定 UI、ログ出力はいずれも入れていない。
この種の常駐ツールは「入れたことを忘れて動き続ける」のが理想で、
機能が増えるほど不具合の原因になり、常駐プロセスとしての信頼性が下がる。

## 受け入れ検証

実際に War Thunder が起動している状態でリリースビルドを走らせた結果:

- `GamesPlayAssist.exe` は起動から **0.25 秒**で終了した
- `aces.exe` (War Thunder 本体) は生存した
- 二重起動したインスタンスは即座に自分で終了した (名前付き Mutex による排他)

単体テストは 7 件。コマンドライン解析のテストには実際に観測した引数列をそのまま使っている。
PEB 読み取りは自プロセスを対象にしたテストで検証している
(他プロセスを読む場合との違いはハンドルの取得元だけ)。

## 未解決

- `GamesPlayAssist` がゲーム (またはランチャー) の起動を仲介しているかどうかは未確定。
  ゲート付きの設計にしたことで、確定させなくても安全に運用できる状態にしてある
- ホットキー登録がフォアグラウンド連動かどうかは推測のまま。設計には影響しない
- 終了させたことが DMM 側のプレイ時間計測や実績に影響するかは未検証
- DMM GAME PLAYER を管理者として起動した場合、`GamesPlayAssist` も昇格するため
  非昇格の本ツールでは終了できないはず (未検証)
